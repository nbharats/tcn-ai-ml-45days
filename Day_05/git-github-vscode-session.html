01

Why Git exists

Just enough theory to answer "what is Git" confidently — no fluff.

Git is a distributed version control system. It tracks every change to your files over time so you can go back, compare, branch off, and merge work — without ever emailing "final_v3_FINAL.py" to anyone again.

GitHub is not Git. Git is the tool that runs on your machine; GitHub is a website that hosts Git repositories in the cloud and adds collaboration features (pull requests, issues, code review, CI/CD). You could use Git your whole life without ever touching GitHub.

Mental model: Git takes snapshots (commits) of your project, not diffs. Each commit points to the snapshot before it — that chain of pointers is your history, and a "branch" is just a movable label pointing at one commit in that chain.
Difference between Git and GitHub is one of the most-asked opening questions in interviews. Answer in one line: "Git is the version control tool, GitHub is a hosting service for Git repositories with collaboration features."

Core Git workflow

The 90% of commands you'll type every single day.

terminal — everyday cycle
git init                       # start tracking a folder
git clone <url>                # copy an existing repo
git status                     # what changed?
git add file.py                # stage one file
git add .                      # stage everything
git commit -m "message"        # snapshot the staged changes
git log                        # history
git log --oneline --graph      # compact visual history
git diff                       # unstaged changes
git diff --staged              # staged changes vs last commit
"Staging area" (a.k.a. the index) is what separates Git from most other VCS. It lets you build a commit out of only some of your changes — interviewers love asking why it exists.

Branching & merging

A branch is a lightweight pointer to a commit. Branching lets you work on a feature without touching main.

terminal — branching
git branch                        # list branches
git branch feature-login          # create a branch
git switch feature-login          # move to it (modern)
git checkout feature-login        # same thing (classic)
git switch -c feature-login       # create + switch in one step

git merge feature-login           # merge into current branch
git branch -d feature-login       # delete merged branch
git branch -D feature-login       # force-delete unmerged branch
Merge conflicts happen when two branches edit the same lines. Git marks the file with <<<<<<< markers — open it, keep the correct code, remove the markers, then git add + git commit.

Remotes & syncing

terminal — remotes
git remote add origin https://github.com/you/repo.git
git remote -v                     # confirm it's set
git push -u origin main           # first push, sets upstream
git push                          # later pushes
git pull                          # fetch + merge remote changes
git fetch                         # download changes, don't merge yet

Undoing things must-know

SituationCommand
Discard unstaged changes in a filegit checkout -- file.py
Unstage a file (keep edits)git restore --staged file.py
Undo last commit, keep changes stagedgit reset --soft HEAD~1
Undo last commit, unstage changesgit reset HEAD~1
Undo last commit, discard changesgit reset --hard HEAD~1
Safely undo a public commit (new commit)git revert <hash>
Temporarily shelve changesgit stash / git stash pop
reset vs revert: reset rewrites history (fine for local/unpushed work), revert adds a new commit that undoes a previous one (safe for shared/pushed history). Interviewers ask this constantly.

Advanced Git

Enough to sound senior in an interview — used less often day-to-day.

CommandWhat it's for
git rebase mainReplay your branch's commits on top of latest main — linear history instead of a merge bubble
git rebase -i HEAD~4Interactive rebase — squash, reword, reorder your last 4 commits
git cherry-pick <hash>Copy one specific commit onto your current branch
git reflogFull log of every HEAD movement — your safety net when you "lost" a commit
git bisect startBinary-search commit history to find which commit introduced a bug
git tag v1.0.0Mark a specific commit as a release point
git submodule add <url>Embed another repo inside yours (e.g. shared libraries)
git blame file.pySee who last changed each line, and in which commit
git worktree add ../hotfix mainCheck out another branch into a separate folder, no stashing needed
Rebase golden rule: never rebase a branch that others have already pulled — it rewrites commit hashes and breaks their history.

GitHub basics

From zero account to your first pushed repo.

  1. Create an account at github.com/signup — use an email you'll check for years (it becomes your dev identity).
  2. Set a clean username — recruiters and interviewers will look at your profile.
  3. Add a profile picture, bio, and pin your best 4–6 repos.
  4. Create a new repository from the + menu → New repository, or push an existing local project into it.
terminal — connect a local project to a new GitHub repo
git init
git add .
git commit -m "initial commit"
git branch -M main
git remote add origin https://github.com/you/repo-name.git
git push -u origin main

SSH keys recommended

SSH auth means you never type your password/token again on that machine.

terminal — generate & add an SSH key
ssh-keygen -t ed25519 -C "you@example.com"
# press Enter to accept default path, set a passphrase (optional)

eval "$(ssh-agent -s)"
ssh-add ~/.ssh/id_ed25519

cat ~/.ssh/id_ed25519.pub
# copy the output → GitHub → Settings → SSH and GPG keys → New SSH key

ssh -T git@github.com
# should say: "Hi username! You've successfully authenticated"

Forks, Pull Requests & team workflow

The standard open-source / team flow:

  1. Fork the repo (your own copy on GitHub) if you don't have write access.
  2. Clone it locally: git clone <your-fork-url>
  3. Create a feature branch: git switch -c fix-navbar-bug
  4. Commit, push to your fork, then open a Pull Request against the original repo.
  5. Respond to review comments, push more commits — the PR updates automatically.
  6. Maintainer merges (or squash-merges) once approved.
Know the difference: a fork is a copy of the whole repo under your account; a branch is a line of development inside one repo. Forks are for outside contributors, branches are for teammates with write access.

GitHub Desktop

A GUI for the exact same Git operations — great for visualizing diffs and history before you're fully comfortable with the CLI. Many working developers still use it alongside the terminal.

desktop.github.comDownload for Windows / macOS
  • File → Clone repository — pick from your GitHub account directly.
  • Changes tab shows a visual diff; write a commit message and hit Commit to main.
  • Push origin button replaces git push.
  • Branch → New branch, and merging is drag-and-drop simple via the History tab.

GitHub Pages, Actions & Gists (good to know)

  • GitHub Pages — host a static site free, straight from a repo (Settings → Pages).
  • GitHub Actions — automate tests/builds on every push (CI/CD), defined in .github/workflows/*.yml.
  • Gist — share a single snippet of code without creating a full repo: gist.github.com.
  • README.md — the first thing anyone sees; always include setup steps and usage examples.

Interview Q&A

The exact questions students get asked most. Click to expand.

What's the difference between Git and GitHub?

Git is a distributed version control tool that runs locally and tracks snapshots of your code. GitHub is a cloud platform that hosts Git repositories and adds collaboration tools like pull requests, issues, and Actions.

What is the difference between git merge and git rebase?

Merge creates a new commit joining two histories, preserving both branches' commit order — safe but creates a "merge bubble." Rebase replays your commits on top of another branch, producing a linear history — cleaner but rewrites commit hashes, so never rebase shared/pushed branches.

What is the staging area?

A middle step between your working directory and a commit. It lets you choose exactly which changes go into the next snapshot using git add, instead of committing everything at once.

How do you resolve a merge conflict?

Open the conflicted file, find the <<<<<<< / ======= / >>>>>>> markers, manually keep the correct code, delete the markers, then git add the file and git commit to finish the merge.

What's the difference between git fetch and git pull?

fetch downloads new commits from the remote but doesn't touch your working branch. pull is fetch + merge (or rebase) in one step, updating your current branch immediately.

What is a detached HEAD state?

When HEAD points directly to a commit instead of a branch — usually after checking out a specific commit hash. Any new commits made there aren't attached to a branch and can be lost unless you create a branch from that point.

How would you undo a commit that's already been pushed?

Use git revert <hash>, which creates a new commit undoing the changes — safe for shared history. Avoid git reset --hard on pushed commits since it rewrites history others may depend on.

What is a pull request?

A request to merge changes from one branch (or fork) into another, opened on GitHub, that enables code review, discussion, and automated checks before the merge happens.
